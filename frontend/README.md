# Frontend foundation

React, TypeScript and Vite application for the SME Cash Flow platform. The application includes authentication, session recovery, organization navigation, a financial dashboard, Customers, Invoices, Payments with full reversals, Expenses with category management, and dedicated financial analytics. Other business modules remain deferred.

Notifications and reminder visibility are implemented in Prompt 10; see the integration notes below.

## Local development

Use Node 22.22.2+, 24.15.0+, or 26+ (supported even-numbered releases). The installed test tooling sets this requirement above [Vite's minimum](https://vite.dev/guide/). From `frontend/`:

```powershell
npm ci
Copy-Item .env.example .env
npm run dev
```

Open `http://localhost:5173`. Run the backend separately from `backend/` using the [backend README](../backend/README.md). Frontend commands still run from `frontend/`. The only required public setting is `VITE_API_BASE_URL`, defaulting in the example to `http://localhost:3000/api/v1`. Configuration rejects missing values, other API paths, embedded credentials, query strings and fragments. Vite variables are public build inputs; never put secrets in them. Supply the deployed API URL at build time.

The backend allows this development origin and credentialed requests. Use `localhost` consistently for both apps. The backend owns its host-only HttpOnly refresh cookie, scoped to `/api/v1/auth`, with SameSite=Lax and Secure in production. Production requires HTTPS and an explicitly approved origin. No security settings or CORS policies are weakened by this frontend. Preview runs on port 4173 and requires its own approved backend origin if API calls are made there.

## Contracts and extension points

`src/api/client.ts` accepts resource paths such as `/health`, relative to the configured `/api/v1` root. Responses retain their complete body, status, headers and request ID; `{data}` and `{data,meta}` envelopes are not unwrapped. Decimal strings, business date strings and opaque cursor metadata are preserved.

```ts
const client = createApiClient({
  baseUrl: environment.apiBaseUrl,
  getAccessToken: () => currentMemoryToken,
});
const response = await client.request('/resource', {
  method: 'PATCH',
  body: { description: 'Updated' },
  ifMatch: '"3"',
  signal,
});
```

The low-level transport accepts an accessor evaluated on each request. Authenticated callers use `useAuth().session.request`, which wraps it with bounded session recovery. `apiClient` remains public transport. Requests include credentials; omitted bodies stay absent and explicit `{}` bodies use JSON Content-Type. Optional idempotency keys and If-Match values are forwarded without inventing domain rules. The transport supports PUT, but the existing backend has no PUT routes and does not allow PUT in CORS.

Use explicit `responseType: 'text'` or `'blob'` for non-JSON responses. Empty responses, including 204/205, return `body: undefined`. Request IDs, ETags and idempotency replay headers are exposed by backend CORS. `Content-Disposition` is not exposed across origins; future download UI will need a documented fallback filename or an approved backend change.

`ApiError` retains status, canonical code, request ID, field paths/codes and optional structured details. User-facing messages are allowlisted; backend free text is discarded. Details are not rendered or logged. Network failures and unexpected responses have safe fallbacks. Cancellation remains cancellation.

The shared QueryClient uses 30-second stale time, five-minute garbage collection, and at most one retry for network/server read failures. Authorization/client errors, malformed responses and cancellation are not retried. Mutations never retry automatically. Query functions must pass their supplied signal into the API client. Organization access uses the stricter policy described below.

CSS Modules style components. The shared Deep Teal visual system lives in `src/styles/tokens.css`; global typography, controls, focus states and reduced-motion rules live in `src/styles/globals.css`. Existing home, login, registration, session and not-found pages consume these tokens through their CSS Modules. The main workspace stays light with blue primary actions. Semantic success, warning and danger text uses darker companion colors for contrast while preserving the approved green, amber and red colors for status marks and fills.

| Role                                  | Token                                                    | Value                             |
| ------------------------------------- | -------------------------------------------------------- | --------------------------------- |
| Future authenticated sidebar          | `--color-sidebar` / `--color-sidebar-text`               | `#123C46` / `#FFFFFF`             |

Spacing, typography, radii, shadows, focus rings and responsive breakpoints use the same global token set. Form fields retain visible labels and have a consistent border, surface, padding and focus treatment. The authenticated workspace consumes `--color-sidebar` and `--color-navigation-active`; its modal scrim uses `--color-overlay`. ## Authentication and recovery

- `/login` signs in with `{email,password}`. `/register` creates a global user with `{email,password,firstName,lastName}`, then returns to sign-in; registration creates no organization, cookie or authenticated session.
- `/session` is a minimal protected confirmation page with sign-out and a workspace link. It is not a dashboard. `/` and not-found routes stay public. Protected routes show a checking state before resolving authentication. Return-to navigation accepts `/session`, `/workspace`, organization workspace/dashboard routes and the implemented customer/invoice list, new, detail and edit routes, with optional query/hash. Organization and resource IDs must be UUID v4.
- Startup performs exactly one `POST /auth/refresh` with `{}`, including under React StrictMode. A valid token response is followed by `GET /me`; authentication is established only after profile verification. Tokens and profiles are runtime-validated. The profile lives in TanStack Query; React Context exposes session status/actions and reads that profile. Tokens never enter query data, browser storage, client cookies or logs. JWTs are not decoded for authority.
- Backend refresh credentials rotate once; reuse returns `401 SESSION_COMPROMISED` and compromises the family. Missing/expired refresh returns `401 INVALID_SESSION`. There is no client retry of rotation, including uncertain network outcomes. Failed restoration leaves a safe sign-in state. Failed logout clears the local session but reports that server revocation could not be confirmed, with an explicit retry action.
- The backend does not distinguish expired access JWTs from other invalid access contexts: both return `401 UNAUTHENTICATED`. With an existing access token, eligible requests may recover once through one shared in-flight refresh promise per application instance. Concurrent and late old-token failures share recovery; the refreshed `/me` identity must match the current account. New requests wait until that identity check completes. 403, noncanonical 401, network failures and uncertain mutation outcomes do not trigger automatic recovery/replay.
- GET reads may replay once. Mutations require explicit `replay: 'idempotent'` and their existing valid 16–128-character printable idempotency key. Future feature owners must verify their endpoint's idempotency contract before opting in. The body, method, If-Match, key, query and caller cancellation remain unchanged. No key is regenerated. A second 401 ends the session, without another refresh.
- Logout/account changes clear credentials and all account-specific query/mutation cache immediately and abort pending resource requests. A generation check prevents old requests from caching results or replaying with a new account. Logout waits for in-flight login/refresh Set-Cookie responses before sending its own revocation/clear-cookie request; an old response cannot restore local authentication. Authentication commands cannot use the recovery wrapper.
- Cancellation stops that caller's wait/replay without aborting shared single-use rotation. Auth cookie operations are serialized against login/logout; access tokens are held in one private in-memory controller. Deduplication is within one application instance; simultaneous refresh in independent tabs remains subject to the backend's strict replay policy.

All authentication POSTs send JSON, including `{}` for refresh/logout. Login failures use generic messages; registration exposes only the backend's safe `EMAIL_UNAVAILABLE` disclosure. Password validation follows 12–128 Unicode characters and a 512-byte UTF-8 ceiling. No password reset, verification, MFA, logout-all UI or tenant administration is added.

## Organization workspace (Prompt 3)

`/workspace` verifies the signed-in account's accessible organizations, then replaces the URL with `/organizations/:organizationId/workspace`. The scoped URL is authoritative for selection. `/session` remains available. Dashboard, Customers, Invoices, Payments and Expenses are actionable under their canonical read permissions; future business entries remain noninteractive and explicitly marked Coming soon.

- `GET /organizations` returns `{data: OrganizationSummary[]}` for all active memberships in active organizations. It is intentionally unpaginated; no search, cursor, limit or pagination metadata is sent or assumed. The native labelled select includes every returned organization and supports browser keyboard navigation and scrolling.
- `GET /organizations/:organizationId` freshly rechecks tenant access and returns organization details and the caller's membership. Nonmembership/inactive access is concealed as 404; a permission rejection is 403. Neither endpoint returns an effective-permissions array. `permissions.ts` mirrors the actual backend canonical role map solely for UI hints; backend checks remain authoritative. Unknown roles and permissions fail closed. JWTs are never decoded for tenant authority.
- `OrganizationProvider` coordinates URL selection and reads TanStack Query data through the existing authenticated session transport. Context exposes the resolved organization, membership, permission hints, access state, switching and explicit retry. Lists and permissions are not duplicated into independent long-lived state. Loading is distinct from confirmed denial. A scoped unavailable ID never silently selects another organization.
- The account-specific `sme.organization.<userId>` localStorage value contains only a selected UUID. It is a hint: a fresh list and detail check must validate it. Invalid/revoked hints fall back to the first freshly accessible organization only at `/workspace`. An empty list stays empty with invitation guidance. Storage failures do not block selection. Workspace sign-out removes that account's hint.
- `organizationKeys.list(accountId)` isolates lists; `scope(accountId, organizationId)` is the prefix for all future tenant data; `context(accountId, organizationId)` isolates membership detail. Switching and browser history cancel/remove the old tenant scope. Account changes remount the provider and the existing session controller aborts requests and clears all caches. Pass Query's cancellation signal through `session.request`; never use previous-tenant placeholder data.
- Access queries use zero stale/unused retention time, no automatic failure retries, and refetch on mount, focus, reconnect and every 60 seconds while successful. Permissions and workspace content are withheld during revalidation or errors. Failed detail authorization waits for an explicit retry or a new selection. This is not instantaneous server-pushed revocation: future commands still require backend authorization on every request.
- The Deep Teal desktop sidebar becomes a modal drawer below 48rem. The drawer locks body scrolling, moves and traps keyboard focus, closes on Escape/backdrop/navigation, restores trigger focus and makes background content inert. It closes when resized to desktop. Workspace navigation uses `aria-current`; sidebar focus outlines use white for contrast.

Tests use MSW and React Testing Library for account/tenant isolation, selection persistence, races, revocation, permission denial, many organizations, empty/error/retry states and drawer keyboard behavior. This milestone does not claim a live backend/browser integration run or implement organization creation, membership administration or financial features.

## Financial dashboard (Prompt 4)

`/organizations/:organizationId/dashboard` is a lazy route inside the existing protected organization shell. Dashboard navigation requires the resolved membership's canonical `analytics.read` hint. Direct access without that hint shows access denied and sends no financial requests. Switching organizations preserves the dashboard destination, freshly verifies the new tenant, resets filters and cancels/removes the old tenant's scope. Workspace and sign-in behavior remain available.

The dashboard composes two existing read endpoints:

| Endpoint                                               | Filters                               | Dashboard use                                                                                                                      |
| ------------------------------------------------------ | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `GET /organizations/:organizationId/analytics/summary` | `fromDate`, `toDate`, `asOfDate`      | Collected cash inflow, active-expense outflow, net cash flow, total currently issued invoices, outstanding and overdue receivables |
| `GET /organizations/:organizationId/cash-flow`         | `fromDate`, `toDate`, `groupBy=month` | Populated monthly inflow/outflow chart and exact-value table                                                                       |

These are aggregate responses without pagination. No invoice pages, collection-rate formulas or frontend financial totals are composed. Collected cash is simplified cash-basis revenue and net cash flow is the net result, so duplicate cards/charts are avoided. The UI explicitly states that this is not a GAAP/IFRS financial statement, historical snapshot or bank balance. Current RECORDED payments and ACTIVE expenses contribute; reversed/voided facts are excluded by the backend. Summary and cash-flow reads have independent backend snapshots, so concurrent updates can differ between cards and the chart.

Presets use organization-local today: current calendar month, previous calendar month and the last 90 inclusive business dates. Custom bounds use real `YYYY-MM-DD` dates, ordered ranges and at most 366 inclusive days. The range start cannot exceed today's receivables as-of date. Receivables always cover all eligible current issued invoices and recorded payments through that as-of date, independently of the selected cash/billing range. Due today is not overdue. Natural month starts label partial buckets; absent buckets are not fabricated.

Money stays in runtime-validated Decimal strings. `decimal.js-light` uses a private 64-digit constructor for display/normalization; BigInt and Intl format grouped integers without Number conversion. Currency scale, response dates/currency/timezone/basis and chronological monthly series are checked before display. Ratios/delays retain their own backend Decimal definitions. Recharts receives only dimensionless normalized bar coordinates; exact amounts remain in cards and a visible accessible table. Green and amber chart colors consume semantic CSS tokens, and animations are disabled. The chart uses the documented [Recharts responsive container](https://recharts.github.io/en-US/api/ResponsiveContainer/).

Financial query keys begin with `organizationKeys.scope(accountId, organizationId)` and include currency, timezone, range, as-of date and grouping. Query signals reach both authenticated reads. No previous-data placeholder or optimistic mutation is used. Pending/refetch/error states withhold financial values. Existing read retry policy permits at most one network/server retry; 401 recovery uses the existing session controller, while 403/404/422 and malformed responses do not automatically retry. Explicit retry remains available. Membership revalidation withholds/unmounts the dashboard when organization access is unresolved or revoked.

Tests cover exact money and chart normalization, timezone/leap-day/range boundaries, lazy navigation, request filters, permission denial, errors/retries, empty/loading states and late old-tenant responses. Recharts is imported only by the lazy dashboard; Decimal is also used by lazy invoice previews. The initial bundle retains the pre-existing size warning; no manual chunking or warning suppression is added. Browser layout and live backend integration are not claimed by the isolated test suite. Other business pages remain deferred.

## Customers (Prompt 5)

The protected organization shell lazily loads `/organizations/:organizationId/customers`, `/customers/new`, `/customers/:customerId` and `/customers/:customerId/edit` (all with the same organization prefix). Customers navigation uses `customer.read`; create, edit and archive actions use the resolved membership's canonical `customer.create`, `customer.update` and `customer.archive` hints. Backend authorization remains authoritative. Organization switching opens the new tenant's list, never carries a customer ID or draft into the new tenant, and aborts obsolete reads and writes. Keys include account, organization, filters and the opaque cursor; late write responses cannot redirect or invalidate another tenant's UI.

Only display name (visible text, maximum 200 characters), optional customer code (50) and optional email (320) are writable. Blank optional fields serialize as null; casing and whitespace are preserved. Codes remain reserved even for archived customers. No address, phone, financial totals, customer count, invoice history, deletion or restoration is invented.

Listing supports ACTIVE/ARCHIVED, literal name/email search (2–100 characters, 300 ms debounce), displayName/createdAt/updatedAt sorting, ascending/descending order and 25/50/100 page sizes. Next uses only the returned `after` cursor; Previous revisits saved cursor history. Search/filter/sort changes reset that history. The displayed count describes this page only. Pending, refetch, invalid and failed responses withhold records. The Deep Teal shell and semantic card/action/status tokens are reused; the desktop table becomes labelled cards below 48rem, forms wrap and confirmation dialogs fit the viewport.

Create has no Idempotency-Key contract. It is submitted once without automatic retries or auth replay; uncertain outcomes block resubmission and direct the user to check the list. Edit preserves the exact quoted response ETag in If-Match; a CONCURRENT_MODIFICATION conflict blocks saving until an explicit reload discards the draft. Optional fields may be cleared, and archived records remain readable/editable as allowed by the backend. Archive is an explicit confirmed POST with `{}`, no If-Match and no Idempotency-Key. It retains the record and references, tolerates an already-archived response and supports explicit idempotent retry after an error. Native modal behavior, focus restoration, Escape and keyboard containment are implemented. All mutations prevent duplicate submission, avoid optimistic changes and invalidate tenant-scoped customer reads after verified success.

Tests use RTL/MSW/Vitest and exercise contracts, forms, ETags, safe errors, cursor navigation, permissions and tenant cancellation. jsdom dialog methods are test shims; real browser layout and live backend integration have not been verified. No new dependencies or chart imports were introduced for Customers.

## Invoice management (Prompt 6)

Four protected lazy routes share `/organizations/:organizationId/invoices`: the directory, `/new`, `/:invoiceId` and `/:invoiceId/edit`. Canonical membership permissions govern navigation and each action; edit is draft-only. Organization switching returns to the destination tenant list, discards drafts, cancels requests and prevents late writes from redirecting or updating the new tenant. Query keys include account, organization, currency, filters and cursor. Backend authorization remains authoritative.

All eight existing APIs are integrated: collection POST/GET, item GET/PATCH/DELETE, and POST issue/cancel/void. Writable inputs are exactly customerId, issueDate, dueDate, discount, taxRate and items (description, quantity, unitPrice, sortOrder). Conceptual notes, terms and purchase-order references are excluded because DTOs reject them. Currency is read-only and organization-owned; the first invoice permanently locks it. Official numbers are assigned only at issuance. Draft customer choices use paginated ACTIVE Customers with search and returned cursors; no full collection is fetched. Directory customer filters also support archived choices.

The directory supports literal invoice-number/customer-name search (300 ms debounce), lifecycle/payment/overdue/customer filters, invoice/due date bounds, five backend sort fields and 25/50/100 page sizes. Date ranges must be valid, ordered and at most 1,825 days apart. Previous revisits saved server-cursor history; filter changes reset it, and invalid cursors offer restart. No aggregate is inferred from a page. Loading, refetch and errors withhold records. Desktop tables become labelled cards below 48rem; forms, items and dialogs fit mobile screens with labelled errors, keyboard controls and modal focus restoration.

Inputs remain decimal strings. A private 64-digit decimal.js-light constructor follows backend ROUND_HALF_UP: round each quantity × unitPrice at currency scale, sum rounded lines, round invoice discount, subtract it, round tax, then total. Unit prices accept four places, positive quantities six, percentage/tax rates six within 0–100. Fixed discounts respect currency minor units and the 13-integer-digit bound; NONE requires zero. Bounds/overflow are checked. BigInt formats grouped amounts without Number money. Previews are informational and never sent as totals; details use verified server amounts. No chart import or dependency is added.

PATCH, draft DELETE and issue preserve the exact quoted ETag in If-Match. Issue/DELETE send `{}`; cancel/void send a visible reason (maximum 500 characters) without If-Match. No invoice API currently supports Idempotency-Key replay, so no key or automatic mutation retry/auth replay is invented. Duplicate submissions are disabled. Conflicts and uncertain outcomes require reload; uncertain creation directs users to inspect the list. Success invalidates invoice reads; lifecycle transitions also invalidate dashboard reads. No optimistic financial updates occur.

Drafts can be edited, issued or deleted under dedicated permissions. Issuance requires positive total and freezes customer name/email, dates, currency, items and totals. Only ISSUED invoices can be cancelled (no payment history) or voided (no recorded payments); the backend rechecks history and state under its lock. Each transition requires confirmation. Terminal documents are retained and cannot be reopened; their residual is not collectible. No payment recording/reversal is added.

Unit and RTL/MSW tests cover Decimal boundaries, invoice flows, bodies/headers, snapshots, permissions, safe errors, pagination, customer selection and tenant cancellation. Native dialog methods are shimmed only in jsdom. Live backend and real-browser integration were not performed. Backend code/schema are unchanged. Prompt 7 adds the payment integration below.

## Payments and full reversals (Prompt 7)

Three protected lazy routes use `/organizations/:organizationId/payments`: the history list, `/new` and `/:paymentId`. There is no payment edit/delete route. Canonical `payment.read`, `payment.create` and `payment.reverse` hints gate navigation and actions; current backend authorization remains authoritative. Organization switching opens the destination tenant list, removes the old scope, aborts reads/writes and discards selections. Return destinations support only these implemented payment routes. Unresolved membership withholds financial content.

Exactly four backend APIs are used: `POST /invoices/:invoiceId/payments`, tenant payment collection/item GET and `POST /payments/:paymentId/reverse`, all under the organization prefix. Recording sends only `{amount,paymentDate,method}`; full reversal sends only `{reason,reversalDate}`. Neither uses If-Match. Reference, notes, transaction IDs, reference search, payment editing, deletion, gateway refunds and partial reversals are absent from the implemented backend and are not invented.

History supports invoiceId/status/method/paymentDateFrom/To, paymentDate/recordedAt/amount sorting, order and 25/50/100 page sizes. Ordered date bounds may be at most 1,825 days apart, matching the backend implementation. Next consumes the returned opaque cursor; Previous revisits saved cursors. Changing filters resets pagination. Invalid cursors offer restart; pending/refetch/error states withhold rows. No aggregate is derived from a page. Desktop history tables become labelled cards below 48rem.

Invoice selection reads one paginated ISSUED invoice page at a time, with backend invoice-number/customer search; paid invoices are excluded from choices. A fresh selected-invoice read checks ISSUED status and positive balance. Recording permits positive partial payments up to that server balance; the server rechecks under its lock. Money remains Decimal strings, accepting at most 15 integer/four fractional places and effective currency minor units without rounding. Trailing zeros do not add effective precision. Dates remain real YYYY-MM-DD strings, defaulting to organization-local today. No unsupported future-date or reversal-order restriction is added.

Each logical record or reversal attempt receives one cryptographic UUID Idempotency-Key before its first submission. The exact key, resource and payload are frozen together. Duplicate submissions, mutation retries and automatic authentication replay are disabled. A network failure, server error or malformed success is an uncertain outcome, not evidence of failure. The user may explicitly retry only that unchanged attempt with its original key or inspect invoice-filtered payment history. A later rejected retry cannot erase an earlier uncertain outcome. Pending attempts live only in account/tenant-scoped runtime QueryClient memory and survive membership revalidation and same-tenant route remounts; successful receipts and definitive rejections clear them. Browser refresh, account/session teardown or organization switching discards them, so reconcile history before starting another attempt after that teardown. Definitive conflicts require explicit authoritative reload before a new attempt. No key or body is logged or persisted in browser storage.

Command responses are verified immutable receipts; `Idempotency-Replayed: true` is acknowledged without treating original settlement as a current snapshot. Recording displays the confirmed receipt and links to a fresh current detail read. Detail/list display server settlement and complete reversal evidence. Fresh reversals require a RECORDED payment on an ISSUED invoice. A labelled native modal requires explicit confirmation, visible reason (maximum 500 characters) and a real reversal date for the entire fixed amount. Original facts remain visible; already-reversed/state/idempotency/settlement conflicts are handled safely. No optimistic changes or client summation of payments occur.

Eligible invoice details link to recording; invoice payment history uses the supported collection `invoiceId` filter. Payments link back to invoices. Confirmed record/reversal invalidates account/tenant-scoped payment, invoice and dashboard reads so the server refreshes settlement. No issued document fields are edited. No new dependency, chart import or build configuration is introduced.

Unit and RTL/MSW tests cover amount/date bounds, contracts, cursor paging, selection, bodies/headers, same-key explicit retry, frozen payloads, duplicate submissions, uncertain outcomes, full reversal, conflicts, cache invalidation, permission denial and stale tenant responses. Auth/dashboard test gates are released during cleanup, including failed assertions; the dashboard loading assertion waits for the financial handler to start instead of timing authentication/organization startup. Assertions and timeout values are preserved. Live backend and real-browser integration are not claimed. Backend financial logic/schema remain unchanged. Prompt 8 adds expense management below.

## Financial analytics (Prompt 9)

Three lazy organization routes use canonical `analytics.read`: `/organizations/:organizationId/cash-flow`, `/profit-loss` and `/receivables-aging`. The sidebar and protected return destinations include these routes. Organization switching preserves the page, resets filters to destination defaults, aborts old reads and removes the old tenant cache. Unresolved membership withholds content; server authorization remains authoritative.

Cash Flow GET uses only `fromDate`, `toDate`, `groupBy=day|week|month`. Profit & Loss GET uses the same dates with `groupBy=none|month`. Real YYYY-MM-DD bounds are ordered and at most **366 inclusive days**; future ranges are allowed. Defaults use the organization's current business month, with current/previous month, last 90 days and custom controls. URLs preserve the applied period/group and browser history. Natural bucket starts may precede the selected start (ISO weeks start Monday); only populated backend buckets appear, without filled gaps. P&L `none` omits the time series entirely.
